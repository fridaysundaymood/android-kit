# Lifecycle

The kit combines independent tools; installing it does not make every external prerequisite available. Run `kit doctor --json` (MCP: `kit_doctor`) and inspect `kit status --json` (MCP: `kit_status`) first. Status includes backend status and release status, including pending plans; it does not approve or execute those plans.

1. **Localize and lint:** `kit verify --scope lint --json` (MCP: `kit_verify` with `scope: "lint"`). The kit runs i18n lint when configured and Maestro lint. Review findings against source and resources.
2. **Build and exercise the UI:** `kit verify --scope device --json` (MCP: `kit_verify` with `scope: "device"`). The build variant defaults to `emuLab.build.variant` and can be overridden with `--args '{"build":{"variant":"<variant>"}}'` or MCP `build`. The kit builds with caching, leases a device, runs instrumentation and all YAML Maestro flows, then releases its lease, including on failure. Set instrumentation `packageName` and `runner` through component arguments; `maestroFlow.appId` can also provide the package name. Build artifacts are selected automatically; missing app or test APKs are blocked. Device tests and Maestro require their installed tools and prerequisites.
3. **Test backend isolation:** `kit verify --scope backend --json` (MCP: `kit_verify` with `scope: "backend"`). Use a disposable local Supabase project and synthetic accounts only. The kit reuses an already-running stack; otherwise it starts one and stops it after verification. Set `backend.file` in `--args` or the MCP request to select a scenario; without one, verification uses `backend_default_suite` when the harness exposes it and reports unsupported otherwise.
4. **Review the whole result:** `kit verify --scope all --json` (MCP: `kit_verify` with `scope: "all"`). Inspect individual results and their evidence; blocked or unsupported stages are not passes. Cleanup still runs after failures.
5. **Plan release:** `kit release plan --plan '<JSON object>' --json` (MCP: `kit_release_readiness` with `plan`). Supply a valid release-gate plan; a missing plan is blocked. Review verification and plans. Planning is not approval or execution. Production writes require the release gate's explicit approval workflow.

The tools keep their own responsibilities: emu-lab handles device and build operations, maestro-flow handles journeys and selectors, the backend harness tests local multi-user behavior, the i18n linter checks display boundaries, and the release gate owns release actions. Direct tool calls use `kit tool <MCP_TOOL_NAME> --args '<JSON object>' --json`, equivalent to calling the named MCP tool with that JSON object. The MCP server exposes each sibling's own tool input schema. Check each tool's published reference for its parameters and external prerequisites. Pass component options to orchestration using `--args '<JSON object>'` or the equivalent MCP arguments: `i18n`, `maestro`, `build`, `instrumentation`, and `backend`.
